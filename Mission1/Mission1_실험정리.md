# Mission 1. 신고자 음성으로 성별 분류

## 1. 문제 정의

음성 원천데이터와 라벨링데이터를 이용해 신고자의 성별을 분류하는 문제이다.

- 입력: 신고자 음성
- 출력: `M` 또는 `F`
- 정답 라벨: 라벨링데이터의 `gender`
- 평가 지표: Accuracy

라벨링데이터에서 입력 처리에 사용한 항목은 문제에서 허용한 `startAt`, `endAt`, `speaker`뿐이다. `gender`는 학습 정답과 평가 정답으로만 사용했다.

## 2. 사용 데이터

최종 실험에는 제공받은 대학부 데이터셋을 사용했다.

| 구분 | 음성 파일 | 라벨 파일 | 용도 |
|---|---:|---:|---|
| Training | 29,200개 | 29,200개 | 모델 학습 |
| Validation | 3,640개 | 3,640개 | 최종 평가 |

음성 파일과 JSON 파일은 파일 ID를 기준으로 연결했으며, 서로 연결되지 않는 샘플은 사용하지 않았다.

## 3. 데이터 분석 및 EDA

### 파일 구조와 연결 관계 확인

Training과 Validation 각각에서 WAV와 JSON의 개수를 확인했다. 두 데이터 분할 모두 음성 파일과 라벨 파일의 개수가 일치했고, JSON의 `_id`와 WAV 파일명 앞부분을 기준으로 매칭할 수 있었다.

### 라벨링데이터 구조 확인

JSON에는 전체 통화의 시작·종료 시점, 발화자 번호, 문장 정보와 성별 등 여러 정보가 포함되어 있었다. 문제 조건에 따라 성별을 제외한 다른 메타데이터는 모델 입력에 사용하지 않았다.

### 통화에 두 사람이 동시에 등장하는 문제

한 통화에는 신고자와 상담원 발화가 함께 포함될 수 있다. 전체 통화를 그대로 사용하면 상담원 음성의 성별 정보가 섞일 수 있으므로, 발화자별 구간을 분리해 비교했다.

## 4. 세운 가설과 실험

### 가설 1: 전체 통화를 사용하면 성별 정보가 섞일 수 있다

전체 통화에는 신고자와 상담원 음성이 함께 포함될 수 있다. 이 경우 모델이 신고자가 아닌 상담원 음성의 특징을 학습할 가능성이 있다고 판단했다.

따라서 `speaker` 값으로 신고자 발화 구간만 골라 연결했다. 이 과정에서 사용한 정보는 허용된 `startAt`, `endAt`, `speaker`뿐이다.

### 가설 2: 고정 길이 입력이 필요하다

음성 길이가 샘플마다 다르기 때문에 Wav2Vec2에 넣기 전에 길이를 통일했다.

- 샘플링레이트: 16 kHz
- 최대 길이: 8초
- 짧은 음성: 0으로 padding
- 긴 음성: 앞부분 기준 8초로 자름

샘플마다 성별에 따라 다른 전처리를 적용하지 않았으며, Training과 Validation에 같은 전처리 규칙을 적용했다.

### 파일럿 실험

| 실험 | 방법 | Accuracy |
|---|---|---:|
| 1차 | 전체 통화 기반 MFCC + 분류기 | 약 0.53 |
| 2차 | 신고자 구간만 사용한 MFCC + 분류기 | 약 0.80 |
| 최종 | 신고자 구간 + Wav2Vec2 fine-tuning | 0.9764 |

MFCC 파일럿에서 신고자 구간을 분리했을 때 성능이 크게 개선되어, 발화자 구간 분리가 중요하다는 가설을 확인했다.

## 5. 최종 모델

최종 모델로 공개 사전학습 음성 모델인 `facebook/wav2vec2-base`를 사용했다.

### 선택 이유

- MFCC처럼 사람이 정한 음향 특징만 사용하는 방법보다 원시 음성의 표현을 직접 활용할 수 있다.
- 음성 분류에 적합한 사전학습 표현을 활용할 수 있다.
- 공개 오픈소스 사전학습 모델이므로 대회 사용 조건에 부합한다.
- 외부 상용 AI API는 사용하지 않았다.

### 학습 설정

- 모델: Wav2Vec2-base
- 학습 epoch: 2
- Batch size: 4
- 입력 샘플링레이트: 16 kHz
- 입력 최대 길이: 8초
- Wav2Vec2 feature extractor: frozen
- 학습 장치: NVIDIA Tesla T4 GPU
- Validation batch size: 1

## 6. 최종 결과

최신 데이터셋 전체 Training으로 학습하고 Validation 전체로 평가했다.

- Training: 29,200개
- Validation: 3,640개
- Validation Accuracy: `0.9763736264`
- Accuracy: `97.6374%`

### 계산 효율성

- Total parameters: 94,569,090
- Active parameters: 94,569,090
- Validation 전체 추론 시간: 1,399.24초
- 샘플당 평균 추론 시간: 0.3844초
- 측정 환경: NVIDIA Tesla T4 GPU

## 7. 과적합 가능성 검토

Validation 데이터를 학습의 역전파에 직접 사용하지 않았고, Training과 Validation을 분리해 사용했다. 따라서 Validation 정답을 학습에 직접 넣은 형태의 데이터 누수는 발생하지 않았다.

다만 Validation 정확도만으로 과적합이 완전히 없다고 단정할 수는 없다. 더 엄격하게 확인하려면 다음을 추가로 확인할 수 있다.

- epoch별 Training loss와 Validation accuracy 추이
- 다른 random seed에서의 성능
- 혼동행렬과 성별별 precision, recall
- 동일 통화 또는 유사 화자 중복 여부

## 8. 규정 준수 확인

- 제공받은 대학부 데이터만 사용
- 외부 데이터셋 추가 사용 없음
- `startAt`, `endAt`, `speaker`만 음성 구간 추출에 사용
- `gender`는 정답 라벨로만 사용
- Validation을 Training 역전파에 직접 편입하지 않음
- Training과 Validation에 동일한 전처리 적용
- 공개 오픈소스 사전학습 모델만 사용
- GPT, Claude, Google Vision 등 상용 AI API 미사용

## 9. 고민했던 점과 최종 판단

### MFCC를 계속 사용할지 Wav2Vec2로 바꿀지

처음에는 구현이 간단하고 빠른 MFCC 기반 모델을 사용했다. 그러나 MFCC는 음성의 정보를 제한된 숫자 특징으로 요약하기 때문에 성능에 한계가 있었다. 신고자 구간을 분리하면 성능이 좋아졌지만, 더 풍부한 음성 표현을 사용하기 위해 Wav2Vec2를 선택했다.

### 전체 통화를 사용할지 신고자 구간만 사용할지

전체 통화를 사용하면 상담원 음성이 섞일 수 있다. 문제의 입력은 신고자 음성이므로 `speaker`별 발화 구간을 이용해 신고자 음성만 구성하는 것이 더 타당하다고 판단했다. 파일럿 실험에서도 이 방식의 성능이 더 높았다.

### 8초 고정 길이를 사용할지 sliding window를 사용할지

문제 힌트에 따라 padding과 sliding window를 검토했다. 최종 실험에서는 구현과 추론 시간의 균형을 고려해 최대 8초 padding/truncation을 적용했다. 긴 통화 전체를 여러 window로 처리하는 sliding window는 향후 개선 대상으로 남겼다.

## 10. 제출 파일 구성

```text
Mission1/
├─ inference.py
├─ train.py
├─ requirements.txt
├─ README.md
└─ model/
   ├─ config.json
   ├─ model.safetensors
   ├─ processor_config.json
   ├─ tokenizer_config.json
   └─ vocab.json
```

`inference.py`는 ZIP 입력과 압축 해제 폴더 입력을 모두 지원하도록 구성했다. 모델 파일은 인터넷에서 다시 다운로드하지 않고 제출물의 `model/` 폴더에서 불러온다.

## 11. 발표에서 전달할 핵심 문장

> 전체 통화를 그대로 사용하면 상담원 음성이 섞일 수 있다는 문제를 먼저 확인했다. 그래서 허용된 `startAt`, `endAt`, `speaker` 정보만으로 신고자 발화 구간을 추출했고, MFCC 파일럿을 거쳐 Wav2Vec2 기반 모델을 선택했다. 최종적으로 Training 29,200개로 학습하고 Validation 3,640개에서 97.64%의 Accuracy를 얻었다.
